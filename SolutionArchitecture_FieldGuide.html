This guide is built for one job: giving an AI Solution Architect in the Colaberry Enterprise AI Leadership Accelerator the working 20% of solution architecture that covers 80% of what shows up in real technical reviews. It is not a computer science degree in a web page. It is a field kit.

PRIMER 01 / 12

Why Solution Architecture Exists

Software gets built whether or not anyone architects it. Solution architecture exists to make sure the shape it ends up with was chosen, not accumulated.

A solution architect's job is to translate an approved business initiative into a technical shape that will still make sense eighteen months and three re-orgs later — and to write down why that shape was chosen, so the decision survives staff turnover. Left alone, systems drift toward whatever the last engineer (or the last AI prompt) found easiest to produce. That drift is invisible in week one and expensive by year two: tightly coupled services that can't deploy independently, a database three teams quietly depend on, a "temporary" batch job now load-bearing for payroll.

The rise of AI-generated technical designs changes what the architect produces, not why the role exists. A model can draft a container diagram, a set of ADRs, and a trade-off matrix in minutes. It cannot tell you whether the load assumptions behind that diagram are real, whether the rejected options were genuinely considered, or whether the design matches your organization's actual operating constraints. That judgment — direct, evaluate, approve — is the 20% this guide covers.

Three related terms, not synonyms

Enterprise architecture sets portfolio-wide standards and roadmaps across every system a company runs. Solution architecture — this guide's subject — designs the technical shape of one approved initiative, inside those standards. System design is the same skill scoped down to interview-length: one component, one whiteboard, forty-five minutes. Everything in this guide is solution-architecture scope: one initiative, real constraints, a real sign-off.

What a solution architect is accountable for

  • Translating approved business requirements into a technical approach with named trade-offs, not a single "best" answer presented as fact.
  • Producing (or reviewing) the artifacts that let someone else — a peer architect, a security reviewer, an auditor — reconstruct the reasoning without a meeting.
  • Owning the non-functional requirements as rigorously as the functional ones: an architecture that meets every feature request but falls over at 3x load has failed.
  • Knowing when not to architect — a two-screen internal tool does not need an event bus. Over-engineering is a failure mode, not a safety margin.
PRIMER 02 / 12

Quality Attributes (Non-Functional Requirements)

Functional requirements describe what the system does. Quality attributes describe how well it keeps doing it — and they are where most production incidents actually originate.

The single most common failure in an AI-generated (or junior-written) architecture document is a quality attribute stated as an adjective instead of a number. "The system should be fast" and "the system should be secure" are not requirements — they cannot be tested, cannot be designed against, and cannot be signed off. Every quality attribute in an approved architecture must carry a measurable target, a way to measure it, and who owns it if it's missed.

CategoryWhat it governsBad (adjective)Good (measurable)
AvailabilityUptime, resilience to failure"Highly available"99.9% monthly uptime; RTO 1 hr, RPO 5 min
PerformanceLatency and throughput under load"Fast response times"p95 < 800 ms at 300 requests/sec sustained
ScalabilityBehavior as load grows or spikes"Scales well"Absorb a 40x traffic spike within 10 min via autoscaling
SecurityConfidentiality, integrity, access control"Enterprise-grade security"AES-256 at rest, TLS 1.2+ in transit, field-level encryption on PII, RBAC via OIDC
MaintainabilityCost and risk of future change"Clean, modular code"Weekly deploy cadence per service; MTTR < 1 hr for Sev-1
Compliance / AuditabilityRegulatory and audit obligations"Fully compliant"Immutable, timestamped decision log retained 7 years (NAIC Model Audit Rule)
InteroperabilityIntegration with existing systems"Integrates easily"Consumes Guidewire Cloud API v2; publishes CloudEvents-formatted domain events
Cost efficiencyUnit economics of running the system"Cost-effective"< $0.85 average cloud cost per transaction at steady-state volume
Usability / AccessibilityHuman effectiveness using the system"User-friendly"WCAG 2.1 AA conformance on all policyholder-facing flows
Quality attributes trade off against each other

You cannot maximize every attribute simultaneously — strong consistency costs availability during a network partition (the practical, everyday face of the CAP theorem); tighter security controls add latency; higher availability costs more. A credible architecture states which attributes were prioritized and which were consciously given up, for a stated reason. See Trade-off Analysis.

PRIMER 03 / 12

Architecture Styles

Monolith, services, and event-driven are not a maturity ladder. Each is correct for a different load shape and team shape — the job is matching the style to reality, not picking the newest one.

StyleShapeStrengthsCosts
MonolithSingle deployable unit, shared database, in-process callsSimple to build, test, deploy, and reason about; cheap transactions; low operational overheadScales as one unit; a bug in one module can take down the whole app; deploy risk grows with codebase size; teams collide on the same release
Service-Oriented / MicroservicesIndependently deployable services, each owning its own dataIndependent scaling and deployment; teams can own a service end-to-end; blast radius of a bad deploy is containedDistributed-systems complexity (network calls replace function calls); eventual consistency; requires real operational maturity (observability, service discovery, contract testing)
Event-DrivenServices communicate by publishing and subscribing to events on a broker, not by calling each other directlyLoose coupling — producers don't know who consumes; natural fit for bursty or async workloads; the event stream doubles as an audit trailHarder to trace a single request end-to-end; eventual consistency by default; needs mature broker infrastructure and schema discipline

Choosing a style against reality, not fashion

  • Load shape. Steady, predictable load tolerates a monolith fine. Bursty, unpredictable load (a catastrophe event generating 40x normal claim volume in a day) favors event-driven, queue-buffered designs.
  • Team shape. One team of six can maintain a monolith faster than they can maintain twelve microservices. Multiple independent teams need service boundaries to avoid stepping on each other.
  • Consistency needs. Financial postings that must be exactly right, immediately, lean toward fewer services and real transactions. Analytics, notifications, and audit trails tolerate eventual consistency easily.
  • Blast radius tolerance. If one bad deploy taking down the entire system is unacceptable, that argues for independently deployable services — but only if the org can operate the resulting complexity.
Applied in this guide

ClaimsIQ is architected as event-driven microservices — justified specifically against its catastrophe-event burst profile (up to 40x normal volume) and its need for an inherent, replayable audit trail for regulators. See ADR-001 for the full decision record, including the rejected monolith-extension option.

The C4 Model

C4 gives every diagram a stated zoom level — Context, Container, Component, Code — so a reader always knows what level of detail they're looking at, and so does the person reviewing an AI-drafted diagram.

LevelAudienceShowsCommon AI-generated mistake at this level
1 — ContextAnyone, including non-technical stakeholdersThe system as one box, its users, and the external systems it talks toSmuggling in implementation detail (a specific database) that belongs two levels down
2 — ContainerTechnical staff, architectsThe deployable units inside the system (services, apps, databases, queues) and their technology choicesDrawing "the backend" as one blob — hiding the actual service boundaries the trade-offs depend on
3 — ComponentThe team building that containerThe internal building blocks of one container and how they collaborateProducing a component diagram for every container instead of the one or two that are architecturally significant — wasted effort, diluted attention
4 — CodeIndividual developers, usually via the IDEClass/module-level detailRarely worth hand-maintaining; generated on demand by tooling, not carried as a static document
Each level nests inside the last. This guide's Document 2 delivers Levels 1–3 for ClaimsIQ; Level 4 is left to IDE tooling.

PRIMER 05 / 12

Architecture Decision Records

An ADR is a short, permanent record of one significant decision: what was decided, what else was considered, and why the alternatives lost. It is the single artifact that makes an architecture auditable months after the meeting where it was decided.

What belongs in every ADR

  • Title & ID — short, specific, numbered (e.g., ADR-003: Host Fraud Scoring on SageMaker Real-Time Endpoints).
  • Status — Proposed, Accepted, Superseded (with a link to what superseded it). Never silently delete a superseded ADR — it's still evidence of why the old approach was reasonable at the time.
  • Context — the forces at play: constraints, requirements, prior decisions that make this decision necessary now.
  • Decision — the one sentence that states what will actually be done.
  • Rejected options — every credible alternative considered, and specifically why it lost. Non-negotiable.
  • Consequences — both the benefits gained and the costs accepted. A decision with no negative consequences listed was not actually reviewed.
The review-lens rule

An ADR without at least one rejected option is not a decision record — it's a decision announcement. When reviewing an AI-generated ADR, the rejected-options section is the first thing to check: a model asked to "write an ADR" will often produce confident prose justifying a foregone conclusion, with no evidence any alternative was genuinely weighed.

Trade-off Analysis

Almost every architecturally significant decision trades one quality attribute for another. Trade-off analysis makes that exchange visible and defensible instead of implicit and forgotten.

A lightweight method — a simplified relative of the formal Architecture Trade-off Analysis Method (ATAM) — covers most real-world decisions: list the credible options, agree the criteria that matter and how much each is worth (weights), score each option against each criterion, and total the weighted scores. Then run a sensitivity check: if a weight shifted by a few points, would a different option win? If yes, the decision is close and worth flagging as such rather than presenting as obvious.

CriterionWeightOption AOption BOption C
Throughput at target scale30%869
Operational overhead (lower is easier — scored inverted)25%694
Cost at scale20%785
Team skill fit15%786
Ecosystem / tooling maturity10%876
Weighted total100%7.257.456.55
State the cost, not just the win

A trade-off matrix that only lists advantages for the winning option is marketing, not analysis. Every row that favors the chosen option should have a companion note on what was given up — the full worked matrix in Document 5 pairs every score with an explicit "what we give up" line.

PRIMER 07 / 12

Key Patterns

A working vocabulary of the patterns that show up in most enterprise architectures — and, just as importantly, what each one costs to adopt.

PatternProblem it solvesCost of adopting it
API GatewaySingle, consistent entry point for auth, rate limiting, routing across many servicesNew single point of failure and latency hop if not made highly available
Circuit BreakerStops calling a failing dependency instead of piling up timeouts and cascading the failure upstreamAdds state and configuration (thresholds, half-open retry timing) that must itself be tuned and tested
SagaCoordinates a multi-step transaction across services without a single distributed transactionRequires designing explicit compensating actions for every step — real engineering effort, not a checkbox
CQRSSeparates the read model from the write model so each can be optimized independentlyTwo models to keep in sync; read model is eventually consistent with the write side
Event SourcingStores every state change as an immutable event, giving a full replayable historySignificant complexity — rebuilding current state means replaying events; schema evolution is hard
Strangler FigMigrates off a legacy system incrementally by routing traffic feature-by-feature to the new systemRequires running both systems and a routing layer for the full migration window — slower than a rewrite, far safer
Backend-for-Frontend (BFF)Gives each client type (mobile, web, partner) its own tailored API layer instead of one generic APIMore services to own and deploy; risk of duplicated logic across BFFs if not disciplined
BulkheadIsolates resource pools (threads, connections) per dependency so one slow dependency can't starve all othersMore resource partitions to size and monitor; under-sizing a bulkhead just moves the bottleneck

ClaimsIQ applies API Gateway, Circuit Breaker, a CQRS-lite read model, and Bulkhead isolation — each justified against a specific failure mode in Document 1 and Document 7.

PRIMER 08 / 12

Fitness Functions

A fitness function is an automated, repeatable test that checks whether the architecture still has the properties it was designed for — not whether the code compiles or the feature works.

The term comes from evolutionary-architecture practice: a system will keep changing after launch, and fitness functions are how you know the changes haven't quietly eroded the architecture's intended shape. Functional tests answer "does this feature work?" Fitness functions answer "is this system still the architecture we approved?" — a different, and frequently skipped, question.

Fitness functionWhat it protects
Dependency-direction check (no service imports another service's internals or database directly)Service boundary integrity
Latency budget assertion in CI (e.g., fail the build if p95 exceeds 800 ms in a load-test stage)Performance NFR
Contract tests between producer and consumer servicesIntegration correctness across independent deploys
Dependency-freshness / CVE scan gateSecurity posture
Coupling / fan-in-fan-out metric threshold on core modulesMaintainability
Why this matters more with AI-generated code

A capable model can write code that passes every functional test while quietly violating architectural intent — for example, having one service read another service's database directly because it was the fastest way to satisfy the prompt. No human reviewing the diff line-by-line may notice. A fitness function that asserts "no cross-service database access" catches that class of defect automatically, every time, forever — which is the point.

PRIMER 09 / 12

Build vs. Buy

Every new dependency is a decision, not a default. The question is always the same: does building this ourselves create an advantage worth its ongoing cost?

DifferentiationMarket maturityTypical callWhy
High — this is core to the competitive advantageLow — no mature product fitsBuildNo vendor will build your differentiator for you; the capability is the point
Low — commodity capabilityHigh — many mature optionsBuyUndifferentiated effort is pure opportunity cost; a vendor already solved it at a scale you can't match
LowLowBuy + extendTake the closest mature option and adapt around its edges rather than building from zero
HighHighBuy, then differentiate elsewhereUse the mature option for the plumbing; spend build effort on the layer customers actually feel

Every "buy" decision still needs three questions answered explicitly: total cost of ownership over a realistic horizon (subscription plus integration plus exit cost) versus building, time-to-value, and the exit path if the vendor relationship ends. A build-vs-buy call with no exit-path answer is not a complete decision.

Applied in this guide

ClaimsIQ buys managed ML hosting (Amazon SageMaker) for fraud-score inference — commodity infrastructure, high market maturity — and builds the claims triage and routing logic in-house, because that logic encodes Meridian's actual underwriting judgment and is the differentiator. See ADR-003.

PRIMER 10 / 12

Good vs. Bad Architecture

Good architecture and over-engineered architecture are both failure states relative to the actual problem. Size the design to the load and the team, not to an imagined future.

SignalGood architectureBad architecture
Trade-offsExplicit, with rejected alternatives on recordImplicit — "this is just how we did it"
Quality attributesEvery one has a measurable target and an ownerDescribed in adjectives ("fast," "secure," "scalable")
ComplexityMatches the actual load and team sizeSpeculative generality — microservices for a two-screen CRUD app "in case we scale"
Failure pathsDesigned before the happy path ships"We'll add error handling later"
DecisionsRecorded in ADRs, reviewable months laterLive only in a Slack thread or one engineer's memory
CouplingExplicit, minimal, tested boundariesEvery service quietly calls every other service's database
Change costA single-service change ships without a multi-team migrationAny change ripples across the whole system unpredictably
Over-engineering is not a safety margin — it's a defect

A design with three more abstraction layers than the problem needs is exactly as much a review finding as a design with none. It costs real money (build time, cognitive load, onboarding time) for protection against a scale or flexibility need that may never arrive. When reviewing an AI-generated design, treat unjustified complexity with the same scrutiny as a missing failure path.

PRIMER 12 / 12

The Architect's Review Lens

This is the checklist you actually run — on your own design, or on one an AI produced in minutes. If a design fails any item below, it is not ready to approve, no matter how polished the diagrams look.

  1. Does every quality attribute have a measurable target, a measurement method, and a named owner — not an adjective?
  2. Is the architecture style (monolith / services / event-driven) justified against actual load and team shape, with the justification written down?
  3. Does every architecturally significant decision have an ADR, and does every ADR list at least one genuinely rejected option with a specific reason it lost?
  4. Do trade-off comparisons state what is given up, not only what is gained, for the chosen option?
  5. Are failure paths — timeouts, retries, circuit breakers, dead-letter handling — designed before the happy path ships, per external dependency?
  6. Are security and compliance boundaries explicit: what's encrypted, who's authorized, what's logged, what's retained and for how long?
  7. Is there at least one fitness function (automated, not narrative) proving each architecturally important property actually holds?
  8. Is there a cost estimate, and does it hold up against the approved budget?
  9. Does every new external dependency have an explicit build-vs-buy justification, including an exit path?
  10. Does the complexity match the problem — no speculative generality, no missing capability the load genuinely requires?
  11. Can a mid-level engineer who wasn't in the design meetings read the package and correctly explain the system back to you?
  12. Is there a named Prepared / Reviewed / Approved chain, with dates — so accountability for the decision is traceable?

CASE STUDYREQUIREMENTS: APPROVED

Meridian Mutual Insurance — ClaimsIQ

The initiative every document in this guide is written against. Requirements below are treated as already approved by the business — this is where the architect's work begins.

The company

Meridian Mutual Insurance Group is a regional property & casualty insurer headquartered in Columbus, Ohio, writing auto and homeowners policies across nine Midwestern states. ~2.1 million policies in force, $1.4B annual written premium. Claims are administered on Guidewire ClaimCenter (system of record); policy and underwriting run on Duck Creek Policy; enterprise integration currently runs through an on-premises Mulesoft ESB; digital channels (mobile app, agent portal) run on AWS.

The initiative

ClaimsIQ is an AI-assisted claims intake and fraud-triage platform. It ingests First Notice of Loss (FNOL) submissions from the mobile app, agent portal, and transcribed phone/IVR calls; runs document intelligence on uploaded photos and PDFs (police reports, repair estimates); verifies coverage against Guidewire and Duck Creek; scores fraud risk with a machine-learning model; and routes each claim to one of three outcomes — straight-through auto-approval and payment, the adjuster queue, or escalation to the Special Investigations Unit (SIU). Guidewire ClaimCenter remains the system of record; ClaimsIQ is an orchestration and intelligence layer, not a replacement.

Sponsorship & approved budget

Executive sponsor: Chief Operating Officer. Business owner: Chief Claims Officer. Year-1 budget approved: $3.4M. The business case, ROI model, and stakeholder sign-off on scope predate this guide — nothing in the documents below revisits whether to fund ClaimsIQ, only how to build it soundly.

1. Introduction & Purpose

This Solution Architecture Document (SAD) defines the technical approach for ClaimsIQ, Meridian Mutual Insurance Group's AI-assisted claims intake and fraud-triage platform. It is the reference of record for the Architecture Review Board, engineering teams, security, and compliance stakeholders. Business requirements referenced throughout are treated as approved prior to this document; the SAD's job is to define how those requirements are met, with every significant technical choice traceable to a written decision.

This document is intended to be read alongside the rest of the ClaimsIQ Architecture Package: the C4 diagrams (Document 2), the Architecture Decision Records (Document 3), the NFR Specification (Document 4), the Technology Trade-off Matrix (Document 5), the Sequence & Data-Flow diagrams (Document 6), and the Risk Register (Document 7).

2. Business Context & Goals

Meridian Mutual processes approximately 450 personal-line claims per day at steady state, rising to as many as 8,000 FNOLs within 24 hours during a regional catastrophe (CAT) event such as a hailstorm. The current manual intake and triage process averages 3.2 business days from FNOL to adjuster assignment, with no systematic fraud pre-screening beyond adjuster judgment. Four business goals, already approved by the Chief Claims Officer and COO, drive every architecture decision in this document:

  • Reduce intake-to-assignment time to under 4 hours for auto and homeowners claims.
  • Straight-through process at least 35% of low-severity, low-risk claims under $5,000 without adjuster touch.
  • Reduce annual fraud leakage by 15% through systematic ML-based triage to the Special Investigations Unit.
  • Maintain full regulatory auditability (state Departments of Insurance, NAIC Model Audit Rule) and achieve SOC 2 Type II attestation.

3. Scope

In scope for v1: personal auto and homeowners FNOL intake (mobile app, agent portal, transcribed IVR), document intelligence on uploaded evidence, policy/coverage verification, ML fraud-risk scoring, rules-based triage and routing, straight-through payment disbursement up to $5,000, SIU escalation workflow, and an immutable audit/compliance log.

Explicitly out of scope for v1: commercial lines claims, litigation management, and subrogation workflow. These are deferred to Phase 2/3 (see Section 15, Roadmap) and remain on existing manual Guidewire workflows until then.

5. Architecture Overview & Principles

ClaimsIQ is architected as an event-driven microservices platform running on AWS, deployed alongside — not in place of — Guidewire ClaimCenter, which remains the system of record for claims and policy data. Services communicate primarily through domain events on a managed Kafka backbone (Amazon MSK), with synchronous REST calls reserved for user-facing request/response paths (intake, status lookups) and for external systems that do not support event delivery. This style is justified in detail in ADR-001 against the CAT-event burst profile (up to 40x normal volume within 24 hours) and the regulatory need for a replayable, immutable audit trail.

Guiding principles

  • Guidewire stays the system of record. ClaimsIQ enriches and orchestrates; it never becomes a second source of truth for claims or policy data.
  • Every routing and fraud decision is explainable. No AI-driven outcome (auto-approval, SIU referral) ships without a human-readable rationale attached to the audit record.
  • Design for the CAT spike, not the daily average. Capacity, autoscaling, and backpressure are designed against the 40x burst case, not steady-state volume.
  • PII is minimized and protected at the point of ingestion, not patched in after the fact.
  • Every service is independently deployable and independently observable. No shared deployment windows, no shared logs without a correlation ID.

6. System & Container Summary

At the Context level, ClaimsIQ sits between policyholders/adjusters/SIU staff and Meridian's existing systems of record (Guidewire, Duck Creek) and external data/payment/identity providers. At the Container level, eleven independently deployable containers handle intake, document intelligence, policy verification, fraud scoring, triage/routing, payment, notifications, audit logging, and analytics export, coordinated through the Kafka event backbone. The full diagrams, with every container's technology stack and every integration's protocol, are in Document 2: C4 Diagrams.

9. Data Architecture

ClaimsIQ classifies all data at ingestion into three tiers: Restricted (SSN, DOB, driver's license, bank account — field-level encrypted and tokenized), Confidential (claim details, adjuster notes, fraud scores — encrypted at rest, access-controlled by role), and Internal (aggregate metrics, anonymized analytics exports). Guidewire ClaimCenter remains authoritative for policy and claim system-of-record data; ClaimsIQ maintains a CQRS-lite read model (Aurora Postgres) for adjuster-facing dashboards and publishes de-identified event copies to Snowflake for actuarial analytics. The full entity-relationship model for the ClaimsIQ read domain is in Document 6.

11. Security Architecture

  • Identity: Okta OIDC for all internal (adjuster, SIU, supervisor) and partner-facing authentication; role-based access control enforced at the API gateway and re-checked at each service.
  • Encryption: TLS 1.2+ for all data in transit; AES-256 at rest for all data stores; field-level encryption and tokenization for SSN, date of birth, and bank account details at the point of ingestion (see ADR-006).
  • Network segmentation: Restricted-tier data stores live in a dedicated private subnet with no direct internet egress; service-to-service traffic inside the VPC only, no public service endpoints.
  • Audit: every fraud score, routing decision, and payment disbursement is written to an append-only audit log with a correlation ID, retained 7 years.
  • Explainability: every AI-driven adverse action (SIU referral, claim denial recommendation) carries a stored, human-readable rationale generated at decision time — not reconstructed after the fact.

12. Deployment & Environment Architecture

All ClaimsIQ containers run on Amazon EKS across three environments — dev, staging, and production — deployed via GitOps (environment promotion through pull request, not manual apply). Production runs across two Availability Zones in us-east-2, with the fraud-scoring SageMaker endpoint and Aurora Postgres both configured Multi-AZ. Infrastructure is defined as code (Terraform); no manual console changes are permitted in staging or production. Config (endpoints, feature flags, thresholds) is externalized via AWS Systems Manager Parameter Store — never hardcoded.

13. Operational Architecture

All services emit structured JSON logs to stdout, collected centrally, with a correlation ID propagated from the initial FNOL submission through every downstream service call and event. Each long-running operation (document intelligence, fraud scoring) emits success/failure rate, retry count, and p50/p95/p99 latency. A CAT-mode runbook defines the manual and automated response when Kafka consumer lag or queue depth crosses a defined threshold during a catastrophe event. On-call rotation and paging thresholds are owned by the Claims Platform Engineering team.

14. Risk Summary

Eight risks are tracked against ClaimsIQ, spanning ML fairness, CAT-event capacity, third-party PII exposure, dependency availability, event-consumer lag, model drift, erroneous straight-through payment, and cloud vendor lock-in. The three highest-scored — ML fraud-model bias, CAT-event traffic overload, and PII breach via a third-party OCR/NLP vendor — carry Critical or High severity and dedicated mitigation owners. Full detail, likelihood/impact scoring, and mitigation plans are in Document 7: Risk Register.

ADR-001Adopt Event-Driven Microservices over Monolithic Extension of Guidewire

Accepted
Date: 2026-03-10Deciders: Solution Architecture, VP Claims Ops, Enterprise ArchitectureRelated: NFR-03, NFR-05
Context

ClaimsIQ must absorb catastrophe-event bursts up to 40x normal daily volume, integrate a real-time ML fraud model, and produce a replayable regulatory audit trail — none of which fit naturally within Guidewire's Gosu scripting extension model or a single-deployable-unit design.

Decision

Build ClaimsIQ as event-driven microservices on AWS, deployed alongside Guidewire, communicating primarily through domain events on a Kafka backbone.

Rejected options
Extend Guidewire ClaimCenter via Gosu scripts/plugins. Tight vendor coupling, quarterly Guidewire release train blocks independent deploys, no native ML integration path, scaling capped by Guidewire's own capacity plan.
Single monolithic service outside Guidewire. Simpler short-term operations, but one bad deploy risks the entire intake pipeline and scaling is all-or-nothing — fails the 40x burst requirement outright.
Consequences

Gained: independent per-container scaling during CAT events; independent team deploy cadence; the Kafka event log doubles as an audit trail.
Given up: materially higher operational complexity (eleven containers instead of one); requires real investment in observability and contract testing; eventual consistency must be designed for explicitly across service boundaries.

ADR-002Use Amazon MSK (Kafka) as the Event Backbone over SNS/SQS

Accepted
Date: 2026-03-17Deciders: Solution Architecture, Platform EngineeringRelated: ADR-001, Trade-off Matrix (Doc 5)
Context

Downstream services need per-claim event ordering, several independent consumer groups reading the same stream (fraud scoring, audit log, analytics export), and the ability to replay historical events to reconstruct an audit trail on demand.

Decision

Amazon MSK (managed Apache Kafka) is the event backbone for all inter-service domain events.

Rejected options
Amazon SNS/SQS. No native per-key ordering guarantee at this fan-out scale without significant workaround; FIFO queues cap throughput and complicate multi-consumer fan-out; no built-in replay of already-consumed messages.
Confluent Cloud (Kafka-compatible SaaS). Stronger tooling ecosystem, but introduces a second vendor billing relationship and a fresh data-residency review outside the existing AWS landing zone. Deferred rather than rejected outright — revisit if MSK's operational cost proves prohibitive at scale.
Consequences

Gained: ordered per-claim event log; unlimited independent consumer groups without redesign; tiered storage supports 7-year-compatible retention.
Given up: the team must operate real Kafka concerns (partition strategy, consumer-lag monitoring) even though MSK is managed; steeper ramp-up for engineers new to Kafka than SQS would have required.

ADR-003Host Fraud Scoring on Amazon SageMaker Real-Time Endpoints

Accepted
Date: 2026-04-02Deciders: Solution Architecture, ML Engineering LeadRelated: NFR-04, Trade-off Matrix (Doc 5)
Context

The production fraud model (XGBoost, tabular features) requires real-time inference at p95 < 3 seconds with autoscaling for CAT bursts. The team has no dedicated ML infrastructure engineers as of program start.

Decision

Host the production fraud model on Amazon SageMaker real-time endpoints with autoscaling and built-in canary/shadow deployment support.

Rejected options
Self-managed inference (Triton/KServe on the existing EKS cluster). Offers more cost control at very high volume, but demands dedicated ML infra operations the team does not currently have — premature at today's ~450 claims/day steady-state volume.
Amazon Bedrock. Evaluated for managed hosting, but at decision time did not support bringing a custom-trained tabular XGBoost model. Rejected on capability fit, not cost.
Consequences

Gained: managed autoscaling absorbs CAT bursts with no dedicated ML ops function required; built-in model versioning and shadow-mode evaluation.
Given up: roughly a 15–20% cost premium per inference versus self-hosting at very high volume; deeper reliance on AWS-specific ML tooling (tracked as Risk R8, accepted as a strategic trade-off).

ADR-004Guidewire Remains System of Record; ClaimsIQ Is an Orchestration Layer

Accepted
Date: 2026-02-20Deciders: COO, Chief Claims Officer, Enterprise ArchitectureRelated: ADR-005, ADR-007
Context

Early planning raised full claims-system replacement as an alternative to a bolt-on intelligence layer. This decision sets the boundary every other ADR in this document operates inside.

Decision

Guidewire ClaimCenter remains the sole system of record for claims and policy data. ClaimsIQ reads, enriches, and writes back through Guidewire's API — it never maintains a competing source of truth.

Rejected options
Full claims-system replacement (build or buy). A 3–5 year program with high regulatory re-certification risk — every state DOI filing is tied to Guidewire's certified claims workflows — plus a heavy adjuster retraining cost. Disproportionate to the approved one-year, $3.4M program.
Dual-write from ClaimsIQ into a new datastore, synced back to Guidewire. Creates two sources of truth with reconciliation risk. Rejected on data-integrity grounds alone.
Consequences

Gained: zero regulatory re-certification risk; adjusters keep their existing tool; program scope stays achievable within the approved year and budget.
Given up: ClaimsIQ inherits Guidewire's API rate limits and availability characteristics as a hard external dependency (tracked as Risk R4); some architectural elegance is sacrificed for integration pragmatism.

ADR-005Direct Guidewire Cloud API Integration for Real-Time Flows, Bypassing Mulesoft ESB

Accepted
Date: 2026-04-15Deciders: Solution Architecture, Enterprise IntegrationRelated: ADR-004, NFR-02
Context

Existing enterprise standard routes all Guidewire traffic through the on-premises Mulesoft ESB. Load testing showed Mulesoft's current capacity adds 1.2–2.5 seconds of latency per call and is provisioned for existing batch volumes, not new real-time synchronous verification traffic.

Decision

New real-time flows (policy verification, claim sync) call the Guidewire Cloud API directly from the Policy Verification Service. Existing batch and legacy flows remain on Mulesoft, unchanged.

Rejected options
Route all new traffic through Mulesoft per the existing integration standard. Would push latency high enough to put the 4-hour intake-to-assignment SLA at risk, and would require an unbudgeted Mulesoft capacity upgrade. Rejected on latency and cost.
Replace Mulesoft entirely. Out of scope — Mulesoft serves dozens of other enterprise batch integrations unrelated to ClaimsIQ. That is an enterprise-architecture-level decision, escalated and logged, not actioned inside this program.
Consequences

Gained: meets the 800 ms p95 API latency target; no new Mulesoft capacity spend required.
Given up: two integration patterns to Guidewire now coexist in the enterprise (direct API and ESB-routed) — Enterprise Architecture has been notified to track this as a documented, intentional exception rather than drift.

ADR-006Field-Level Encryption and Tokenization for PII at Point of Ingestion

Accepted
Date: 2026-04-22Deciders: CISO, Solution ArchitectureRelated: NFR-06, NFR-07, Risk R3
Context

SSN, date of birth, and bank account details flow through multiple services (Intake API, Policy Verification, Payment Disbursement). Database-level encryption at rest alone does not protect PII while it is in memory, in transit between services, or in logs — nor does it limit blast radius if a single service is compromised.

Decision

Tokenize SSN, DOB, and bank account fields at the Intake API boundary. Downstream services operate on tokens only, detokenizing exclusively at the specific point of use (e.g., Payment Disbursement detokenizes the bank account only at the moment of the Fiserv call).

Rejected options
Database-level encryption at rest only. Does not protect data in transit between services or in logs, and does not limit breach blast radius to a single compromised service. Insufficient for SOC 2 Type II and state DOI expectations.
Encrypt but do not tokenize (pass encrypted blobs, decrypt where needed). Reduces exposure somewhat but still requires every downstream service to hold decryption capability, widening the attack surface versus a token boundary.
Consequences

Gained: real PII values are only ever handled by two services in the entire platform; every other service and every log line sees tokens only.
Given up: added tokenization-service dependency and latency (~15–20 ms per detokenize call); the token vault becomes a new critical-path dependency with its own availability target.

ADR-007CQRS-lite Read Model in Aurora PostgreSQL for Adjuster Dashboards

Accepted
Date: 2026-05-06Deciders: Solution Architecture, Guidewire DBA TeamRelated: ADR-004, Risk R5
Context

Adjuster and supervisor dashboards need high-frequency, flexible queries (queue views, filters, aggregates). Guidewire's OLTP database is not provisioned to serve this load without risking contention against Guidewire's own transactional workload.

Decision

Maintain a purpose-built read model in Aurora PostgreSQL, populated by consuming ClaimsIQ's own domain events, serving all adjuster- and supervisor-facing dashboard queries.

Rejected options
Query Guidewire's database directly for dashboard views. Performance risk to the system of record; Guidewire's DBA team declined to certify direct high-frequency read access from an external system.
Real-time sync to Snowflake as the dashboard's query source. Snowflake's batch ingestion latency (~15 minutes) does not meet the sub-second refresh adjusters were promised, and is over-engineered for what is fundamentally an operational, not analytical, workload.
Consequences

Gained: sub-second dashboard queries with zero contention risk to Guidewire; the read-model schema can evolve independently of Guidewire's schema.
Given up: a second data store that must stay eventually consistent with the event stream; a consumer-lag incident could show adjusters a stale queue view (mitigated by the lag-alerting fitness function — see Document 7, Risk R5).

Glossary

Terms used throughout this guide, defined once.

ADR
Architecture Decision Record — a short document capturing one significant decision, its rejected alternatives, and its consequences.
ATAM
Architecture Trade-off Analysis Method — the formal method this guide's lightweight trade-off matrices are adapted from.
C4 Model
A four-level diagramming approach (Context, Container, Component, Code) that scopes every architecture diagram to a stated zoom level.
CAT Event
Catastrophe event — a regional incident (e.g., hailstorm) generating a large burst of claims in a short window.
Circuit Breaker
A pattern that stops calling a failing dependency after repeated failures, preventing cascading failure upstream.
CQRS
Command Query Responsibility Segregation — separating the read model from the write model so each can be optimized independently.
DORA Metrics
Four delivery-performance metrics — deployment frequency, lead time for changes, change failure rate, and MTTR.
Fitness Function
An automated, repeatable test that verifies an architectural property (not just a functional behavior) continues to hold.
FNOL
First Notice of Loss — the initial claim submission a policyholder files after a loss event.
NFR
Non-Functional Requirement — a quality attribute (availability, performance, security, etc.) with a measurable target.
SIU
Special Investigations Unit — the team that investigates claims flagged as high fraud-risk.
Straight-Through Processing
A claim that is auto-approved and paid without any human adjuster touching it.
System of Record
The single authoritative source of truth for a given type of data — for claims and policy data, that remains Guidewire ClaimCenter.
Tokenization
Replacing a sensitive value (like an SSN) with a non-sensitive reference token, so downstream systems never handle the real value.
